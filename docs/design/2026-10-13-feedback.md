# Feedback: report a problem or suggest an improvement

Status: approved by the owner on 2026-10-12. This document describes the design; the implementation plan is
`docs/plans/2026-10-13-feedback.md`.

## Goal

Anyone signed in can report a problem or suggest an improvement from any page, with a picture of the screen attached
automatically. The reporter follows what happens to it, and an Admin works through every report. The feature copies
the one already running in the company's PC49 app (`PC49_WEBAPP`, migrations 0036, 0037, 0042, 0043, 0088), adapted to
this app.

The owner's decisions (2026-10-12):
- Follow the PC49 pattern:
  - a header button;
  - a short form with a required description;
  - an automatic screenshot;
  - status changes with a note the reporter reads, and a reason required when a report is declined;
  - an unread count in the menu.
- Three kinds. The second is this app's counterpart of PC49's "a figure is wrong": the machine read a value on a sheet
  wrongly, or missed it.
- The migration runs from the office network together with 0004. This work merges only after it is live.

## What the reporter sees

- **Entry point:**
  - Every signed-in page, the editor included, has a header button with the lucide `MessageSquareWarning` icon.
  - The button's visible label is "Report" (hidden below 640 px). Its accessible name is "Report a problem or
    suggest an improvement".
  - A menu link **Feedback** (`/feedback`) sits beside Sheets and Guide.
- **The dialog** (the app's existing `Dialog` component):
  - **Kind** (radios, default the first):
    - "Something is broken"
    - "A value was read wrongly or missed"
    - "A suggestion"
  - **Impact** (radios, default the second):
    - "It stops my work"
    - "There is a way round, but it costs time"
    - "Minor"
  - **Description:**
    - Required: at least 5 characters after trimming, at most 4,000.
    - Label "What happened?".
    - Placeholder "What were you doing, and what did the app do? Name the sheet and the value if there is one."
    - Send stays disabled until the text is long enough.
  - **Filed from:** a read-only line naming the page, e.g. "Filed from: Sheets" or "Filed from: the editor, sheet
    <name>".
  - **Screenshot:**
    - Taken as the dialog opens, before it paints over the page, with `modern-screenshot` (`domToPng(document.body,
      { scale: 0.6 })`).
    - Nodes marked `data-feedback-chrome` and the dialog itself are filtered out.
    - A checkbox "Send the screenshot with it", on by default, sits above a preview.
    - A privacy line follows: "The picture can show order numbers and sheets. Only you and the Admins can open it."
    - If the capture fails: "The screen could not be captured. The report still sends, without a picture." There is
      no retake, and only one picture.
- **After sending:**
  - The dialog body becomes a thank-you panel: "Sent. The page you were on went with it. Follow it under Feedback."
  - If the picture could not be stored, the panel adds "The report was sent, but the screenshot could not be
    stored."
  - Two buttons: "Report something else" and "Close".
  - Validation and server errors show inside the dialog, which stays open.

## The Feedback page (`/feedback`)

- **One page for everyone; row-level security decides what each person sees.**
- **Staff:**
  - Their own reports, newest first.
  - Columns:
    - Date
    - What it is (kind and impact; "It stops my work" highlighted)
    - What happened (the text, then the Admin's note under it)
    - Filed from (a link to the page, and a "Screenshot" link when there is one)
    - Status
  - An "Updated" badge marks a report whose status or note changed since the person last opened the page.
- **Admin:**
  - Every report.
  - Status tabs with counts: All, New, Looking at it, Fixed, Not doing. They are in the address as `?status=`.
  - Each row also shows the reporter's name, a status select and a note field ("A note for the reporter").
    - Choosing a status saves at once.
    - Leaving the note field after a change saves the note.
    - Choosing "Not doing" with an empty note does not save; it asks for the reason.
- **Statuses:** New, Looking at it, Fixed, Not doing. Any status may move to any other (as in PC49). A move to Not
  doing needs a note.
- **Screenshot links:**
  - Short-lived signed URLs (10 minutes), opened in a new tab.
  - Signed by the reader's own session, so the storage policy decides.
- **Paging:** numbered pages with the shared `Pagination` component, 25 a page.
- **Errors:** a load error shows the error message; an empty list must never pretend all is clear.
- **The unread count:**
  - Shown on the Feedback menu link as a small red number, with an accessible label such as "3 waiting".
  - For an Admin it counts New reports. For Staff it counts their own reports updated since their last visit.
  - Opening `/feedback` marks it seen. There is no email.

## Data (migration 0005)

- **`feedback_reports`:**
  - Columns:
    - `id uuid` primary key
    - `kind` (`broken` | `misread` | `suggestion`)
    - `impact` (`blocking` | `slows_work` | `minor`)
    - `description` (trimmed length 5–4000)
    - `page_url` (≤ 500)
    - `page_route` (≤ 200)
    - `page_label` (≤ 200)
    - `screenshot_path` (nullable)
    - `status` (`new` | `looking` | `fixed` | `declined`, default `new`)
    - `triage_note` (≤ 2000)
    - `reporter_id` (FK to profiles)
    - `created_at`
    - `triaged_by`
    - `triaged_at`
  - Constraint: a declined report has a non-empty note.
  - Indexes on `(status, created_at desc)` and `(reporter_id, created_at desc)`.
- **Row-level security:**
  - Insert: an allowed user, with `reporter_id = auth.uid()`, `status = 'new'` and no triage fields.
  - Select: the reporter, or an Admin.
  - No update policy and no delete policy.
- **A filed report is evidence.** A `before update` trigger refuses any change except:
  - the triage columns, through the status function;
  - a single null → path change of `screenshot_path`.
- **`set_feedback_status(p_id, p_status, p_note)`:**
  - `security definer`, with `search_path = public, pg_temp`.
  - It restates the Admin check itself, because a definer bypasses RLS: `if not is_admin() then raise exception
    'forbidden'`.
  - It enforces the decline reason, keeps the old note when `p_note` is null, and stamps `triaged_by` and
    `triaged_at`.
  - It writes `feedback.status` to the audit log through `_audit`, with the old and new status.
- **Filing writes `feedback.file`** to the audit log from a `security definer` trigger.
- **The screenshot:**
  - Bucket `feedback-screenshots`: private, 5 MB, `image/png` only.
  - The **browser uploads** the PNG directly with the reporter's session. A server action body is limited to 1 MB,
    and the sheet upload already works this way.
  - The path is `<report id>/<uuid>.png`.
  - Storage insert is allowed when the path matches, the report is the caller's own, and no screenshot is attached
    yet.
  - Storage read is allowed to the reporter or an Admin.
  - No update and no delete.
  - **`attach_feedback_screenshot(p_report_id, p_path)`** (`security definer`) links the file. It checks:
    - the caller owns the report;
    - nothing is attached yet;
    - the path is valid;
    - the object exists.
    It raises otherwise.
- **`feedback_seen`** holds `(user_id primary key, seen_at)`. Each person can read and write only their own row.
- **`feedback_unseen()`** (security invoker) returns the badge count as described above.
  **`mark_feedback_seen()`** upserts the caller's row.
- **Audit page:**
  - A new action group **Feedback**, with labels for `feedback.file` and `feedback.status` in both languages.
  - A message icon.
- Every new function is revoked from `public` and `anon` and granted to `authenticated`, as 0004 does.
- The migration is re-runnable (`create … if not exists`, `drop policy if exists`, `create or replace`) and sets
  `lock_timeout`, so the SQL tests can apply it inside a rolled-back transaction, like 0004.

## Deploy order

Apply migrations 0004 and 0005 before this code deploys; until then the Report button says the report was not sent and Feedback says it could not be loaded; no other page is affected.

## Security and privacy

- Screenshots can show order numbers and real sheets. They are private, and only the reporter and Admins can read
  them.
- A report is written once and never edited.
- The description is plain text; it is shown as text and never as HTML.
- The signed links last 10 minutes.
- The CSP needs no change: `img-src` already allows `data:` and `blob:`, and the capture runs in the page.

## Testing

- **SQL** (office network, rolled back):
  - filing (own only, as `new`, without triage fields);
  - reading (own, Admin all);
  - the evidence trigger;
  - `set_feedback_status` (Admin only, decline needs a note, audit entry written);
  - the screenshot (own folder only, one only, attach checks, read rights);
  - unseen counts and marking seen;
  - grants;
  - re-running the migration.
- **Unit:**
  - the form schema (kinds, impact, length limits);
  - the page label for a route;
  - the status-change rules shown in the UI;
  - parsing `?status=`.
- **End-to-end** (production, outside working hours):
  - Staff files a report with a screenshot from the editor;
  - the Admin sees it as New, with a count on the menu, opens the screenshot, and declines without a note (refused)
    and then with one;
  - Staff sees the note and the "Updated" badge, and the count clears after opening the page;
  - another staff member cannot see the report.
- **Guide:** a short section "Report a problem", in both languages, with no new screenshot.
